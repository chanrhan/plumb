# 실행 · 진행 상황 화면 (`/runs`)

이슈 #2의 산출물. `docs/screens/README.md`(공통 레이아웃 2, 출처 접두어 2.1, 프로세스 모델 3.1, API 3.3)를 전제로 한다. 파이프라인은 기획안 §8.3, 이의 제기는 §8.4, 예산·반복 상한은 §15.4.

진행 상황의 출처는 README 3.1 그대로 **`저장소: runs/<id>.json` 폴링**이다. `plumb run` 은 분리된 자식 프로세스이고 UI 서버는 그 파일만 읽는다. 에이전트의 자기 보고("구현했습니다")는 어디에도 표시하지 않는다. 상태와 타임라인은 도구가 직접 실행했거나 가로챈 실행 출력에서만 만든다 (§8.3).

## 1. 목적

**지금 에이전트가 어디까지 했나.** 파이프라인 ①~⑥ 의 현재 위치, 어느 역할이 몇 번째 반복인지, 얼마를 썼는지, 끝났다면 어떻게 끝났는지를 한눈에 보인다. 실행을 시작하는 버튼도 여기 있다.

## 4. 동작

**새 실행.** `[▶ 새 실행]` → 패널 → 승인된 규칙 체크 → `[시작]` → `POST /api/runs { ruleIds }` (토큰 쿠키 필수, 없으면 401). UI 서버가 `plumb run --detach --rules …` 를 `detached: true` 로 spawn 하고 `{ id }` 를 돌려준다 (README 3.1). 화면은 `/runs?id=<id>` 로 이동해 폴링을 시작한다. 패널은 닫힌다.

**폴링.** 선택된 실행이 `진행중` 인 동안 1~2초마다 `GET /api/runs/:id` (README 3.1 "첫 슬라이스는 폴링. SSE는 필요해지면"). `status` 가 종료 상태로 바뀌면 폴링을 멈춘다. 실행 목록은 10초마다 `GET /api/runs`. UI 서버를 재시작해도 `plumb run` 은 살아 있으므로 (README 3.1) 화면을 다시 열면 같은 파일에서 이어 그린다.

**단계 표시.** `stage` 가 n 이면 ①~(n-1) 은 ✔, n 은 ●, 나머지는 빈칸. ⑤에서 ②로 되돌아간 경우(검사가 약함) `stages[]` 에 같은 단계가 두 번 나타나고, 화면은 가장 최근 항목으로 그리며 "2회차" 를 덧붙인다.

**이의 제기.** `disputes[]` 가 비어 있지 않으면 줄이 `⚠ n건` 으로 바뀌고 펼치면 각 건의 시각 · 제기 역할 → 재검토 역할 · 요지. 판정(두 해석이 갈림 → "규칙 진술이 모호함")은 M10 검토 대기열 화면의 몫이고 여기서는 "검토 대기열에 올라감" 만 표시한다.

**중단.** `[중단]` → "실행 r-0003 을 중단합니까? 지금까지의 테스트 파일과 구현은 worktree 에 남습니다" → 확인 → 중단 요청. UI 서버가 `runs/<id>.json` 의 `pid` 로 SIGTERM (README 3.4). `plumb run` 이 `status: 중단` 을 쓰면 화면이 폴링으로 반영한다. 버튼을 누른 뒤 응답을 기다리는 동안은 "중단 요청함…".

**오류 상태.**

| 상황 | 화면 |
|---|---|
| `POST /api/runs` 401 | 패널에 "실행되지 않음: 세션 없음. `plumb ui` 를 다시 시작하면 `/auth` 로 열립니다" |
| `POST /api/runs` 400 (승인 안 된 규칙, 또는 대기열 상한으로 신규 제안 중단 중 — M10) | 패널에 서버 메시지 그대로. 체크박스는 유지 |
| `POST /api/runs` 500 (spawn 실패: `plumb` 바이너리 없음, 샌드박스 설정 오류 등) | 패널에 "실행 프로세스를 시작하지 못함: <메시지>". 목록에 항목이 생기지 않는다 |
| 진행 중인데 `updatedAt` 이 60초 넘게 그대로 | 상세 머리에 "⚠ 60초 넘게 갱신 없음. 프로세스가 멈췄을 수 있습니다 (pid 4812)". 상태는 바꾸지 않는다 (파일이 진실) |
| `runs/<id>.json` 파싱 실패 (쓰는 도중 읽음) | 직전에 성공한 응답을 그대로 두고 다음 폴링을 기다린다. 3회 연속 실패면 "진행 파일을 읽지 못함" |
| `runs/<id>/output.log` 없음 | 출력 블록에 "아직 실행 출력 없음" (5절) |
| 이미 진행 중인 실행이 있을 때 `[▶ 새 실행]` | 첫 슬라이스는 동시 1개. 버튼 비활성 + "r-0003 이 진행 중" (열린 질문 1) |

## 5. 비어 있을 때

목 데이터는 쓰지 않는다. 없으면 "아직 없음" 이다.

| 없는 것 | 화면 |
|---|---|
| `runs/` 디렉토리 없음 또는 빈 목록 | 목록: "실행 아직 없음". 상세 영역은 비어 있음. `[▶ 새 실행]` 은 승인된 규칙이 있으면 활성 |
| 승인된 규칙 0개 | `[▶ 새 실행]` 비활성 + "승인된 규칙이 없습니다. `/rules` 에서 승인하세요". 패널의 규칙 목록은 잠정 규칙만 `선택 불가` 로 보인다 |
| 규칙 자체가 0개 | 위와 같고 메시지는 "규칙이 없습니다" |
| 실행은 있으나 아직 단계 ② 시작 전 (spawn 직후) | 단계 ① ✔, ② 빈칸, 현재 역할 `—`, 반복 0, 예산 $0.00, 출력 "아직 실행 출력 없음" |
| `output.log` 없음 | "아직 실행 출력 없음" |
| `disputes[]` 비어 있음 | "이의 제기: 없음" |
| `costUsd` 없음 (SDK 가 비용을 안 줌) | "예산 — / $10.00 (비용 정보 없음)". 0 으로 보이지 않는다 |
| `plumb.config.json` 에 상한 없음 | 패널에 "상한 없음 (plumb.config.json 에 roles.*.maxBudgetUsd 를 적으세요)". 첫 슬라이스는 상한 없는 실행을 허용하지 않는다 (§15.4) → `[시작]` 비활성 |

## 6. 열린 질문

1. **동시 실행 수.** 첫 슬라이스는 1개로 둔다 (worktree 충돌, 예산 합산이 단순). M10 에서 규칙별 worktree 분리와 함께 재검토.
2. **중단 API.** README 3.3 표에 중단이 없다. `POST /api/runs/:id/abort` 를 제안한다. UI 서버가 pid 로 시그널을 보내는 것이 README 3.4 의 "감수하는 것" 과 맞는지, 아니면 `runs/<id>.abort` 파일을 두고 `plumb run` 이 폴링하는지. → #5 와 M6.
3. **pid 생존 여부.** `kill -0` 결과는 README 2.1 의 다섯 접두어 어디에도 깔끔히 들어가지 않아 화면에서 뺐다. "60초 넘게 갱신 없음" 경고로 대신한다. M6 에서 필요하면 접두어 규칙을 보완(README 2.1)하거나 `plumb run` 이 heartbeat 를 `updatedAt` 에 쓰게 한다.
4. **`RunState` 타입** (→ #5). 이 문서가 쓴 필드: `id` `pid` `status` `reason` `stage` `stages[]` `currentRole` `ruleIds[]` `roles.{role}.{turns,stopBlocks}` `costUsd` `disputes[]` `startedAt` `updatedAt` `finishedAt`. ⑤→② 되돌아감을 `stages[]` 의 반복으로 표현할지 `attempt` 카운터로 할지.
5. **실행 출력의 보관.** `runs/<id>/output.log` 에 명령별로 구분자를 넣고 꼬리 N줄(제안: 20줄)을 보이는지, 명령별로 마지막 것만 보이는지. 크기 상한. 전체 로그 보기는 M10.
6. **비용의 원자료.** SDK 결과 메시지의 비용 필드를 그대로 쓰는지, 토큰 수 × 단가로 UI 서버가 계산하는지. "추정" 표기는 어느 쪽이든 유지.
7. **README 보완 후보.** 3.3 API 표에 (a) 중단, (b) `POST /api/runs` 의 400 조건 (미승인 규칙 · 상한 중단), (c) 실행 출력 꼬리를 `GET /api/runs/:id` 가 같이 주는지 별도 경로인지가 없다. #5 에서 정한다.
