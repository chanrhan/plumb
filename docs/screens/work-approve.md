# 규칙 목록 · 승인 화면 (`/rules`)

이슈 #2의 산출물. `docs/screens/README.md`(공통 레이아웃 2, 출처 접두어 2.1, 승인 통로와 토큰 3.2, API 3.3)를 전제로 한다. 규칙 YAML은 기획안 §5.2, 상태 다섯 가지는 §7.3, 승인 모델은 §9.1·§9.2.

## 1. 목적

**무엇을 승인할 것인가.** 에이전트나 개발자가 제안한 규칙(추가·변경·삭제)을 사람이 읽고 승인·기각하는 유일한 화면이다. 승인은 이 화면(토큰 쿠키)과 `plumb approve`(CLI) 두 통로뿐이고, 에이전트는 둘 다 쓸 수 없다 (README 3.2).

## 4. 동작

**목록 → 상세.** 행 클릭 → URL `/rules?id=pay.refund-window` → `GET /api/rules/:id` → 오른쪽 상세 교체. 블록 트리 클릭 → `?block=` 필터, 목록은 `GET /api/rules` 응답을 클라이언트에서 거른다.

**승인.** `[승인]` → `POST /api/rules/:id/approve`. **이 요청은 README 3.2의 토큰 쿠키(httpOnly · SameSite=Strict, `plumb ui` 시작 시 `/auth?token=T` 로 한 번 심긴다)가 있어야 동작한다.** 쿠키가 없거나 틀리면 401이고, 화면은 승인되지 않았음을 분명히 보인다 (아래 표). 응답 200이면 승인 상태가 `승인` 으로 바뀌고 `⚠ 미확인` 이 사라지며 상단 바 `⚠ n` 이 1 준다. 상태(🟢 등)는 바뀌지 않는다. 승인은 검사가 아니다.

**사전 승인이 필요한 변경 (M10).** `⚡` 고위험 규칙의 완화·삭제·블록 경계 변경은 승인 전까지 저장소의 기존 규칙이 유효하다. 상세에 "승인 전까지 기존 규칙 유효" 를 보이고, 승인하면 그 시점에 제안 버전이 현재 버전이 된다. 일반 영역의 완화·삭제는 즉시 적용되어 있으므로 "적용됨 · 병합 전 확인 필요" 로 구분한다 (§9.1).

**기각.** 사유 입력 → `[기각]` → `POST /api/rules/:id/reject { reason }`. 응답 200이면 승인 상태 `기각`, 목록의 기본 필터에서 숨는다. 사전 승인 대기 중이던 변경을 기각하면 기존 규칙이 그대로 남는다.

**대기열 상한.** 잠정 20건 초과 또는 14일 초과 체류면 머리에 경고 띠. M10부터는 이 상태에서 `plumb run` 의 신규 제안이 중단되므로(§9.2) 띠에 "실행 화면의 새 실행이 제안을 만들지 않습니다" 를 덧붙인다.

**오류 상태.**

| 상황 | 화면 |
|---|---|
| `POST …/approve` 또는 `…/reject` 401 | 버튼 옆에 "승인되지 않음: 세션 없음. `plumb ui` 를 다시 시작하면 `/auth` 로 열립니다". 승인 상태 표시는 그대로 잠정 |
| `POST …/approve` 409 (제안이 화면을 연 뒤 바뀜: 재제안 또는 CLI에서 이미 승인) | "이 규칙이 바뀌었습니다. 다시 읽습니다" → `GET /api/rules/:id` 재요청. 버튼은 다시 읽은 뒤 활성 |
| `GET /api/rules` 가 `rules.yaml` 파싱 오류 | 목록 대신 "rules.yaml 을 읽지 못함: <줄 번호 · 메시지>". 승인 불가 |
| 보호 저장소 변조 증거 (상단 바 "변조 증거") | 승인 · 기각 버튼 비활성, "저장소 검증 실패 상태에서는 승인하지 않습니다" (M10 해시 체인. M3는 발생하지 않음) |
| 검사 파일 `[IDE ↗]` 실패 | `work-views.md` 4절과 같다 |
| `decision` 이 가리키는 `D-xxxx` 파일 없음 | 결정 기록 자리에 "D-0029 파일 없음". 승인은 막지 않는다 (열린 질문 4) |

## 5. 비어 있을 때

목 데이터는 쓰지 않는다. 없으면 "아직 없음" 이다.

| 없는 것 | 화면 |
|---|---|
| `rules.yaml` 없음 또는 빈 목록 | 목록: "규칙 아직 없음. `plumb rule draft` (M3) 로 만들거나 `rules.yaml` 에 직접 적습니다". 상세 영역은 비어 있음. 머리 `미확인 0건` |
| 규칙은 있으나 선택 안 함 | 상세: "왼쪽에서 규칙을 고르세요" |
| 잠정 규칙 0건 | 머리 `미확인 0건`. 경고 띠 없음 |
| 검사 결과 이력 없음 (`plumb check` 를 안 돌림, M5 전) | 상태 전부 ⬜, 커밋·시각 자리 `검사 없음` |
| `checks[]` 비어 있음 | 상세 "검사 없음" 과 ⬜ (§6.3 예시의 `⬜ 로그아웃 시 세션 무효화  검사 없음`) |
| `depends_on[]` 비어 있음 | "의존 없음" |
| `decision` 없음 | "결정 기록 없음" |
| 승인 이력이 제안 하나뿐 | 이력 한 줄. diff 는 전부 `+` |
| 필터 결과 0건 | "조건에 맞는 규칙 없음" + 필터 해제 링크 |

## 6. 열린 질문

1. **제안 기록의 저장 형식** (→ #5). `rules.yaml` 하나에 현재 버전과 제안 버전을 같이 두는가, 제안은 `proposals/<id>.yaml` 로 따로 두는가. diff · `changeKind` · `proposedBy` · `proposedAt` 이 어디 있는지에 따라 `GET /api/rules/:id` 응답 타입이 달라진다.
2. **승인 단위.** M3는 규칙 하나, §9.2는 결정 기록 하나로 묶인 규칙 묶음이다. M3에서 `POST /api/rules/:id/approve` 로 시작하고 M10에서 `POST /api/decisions/:id/approve` 를 더하는지, 처음부터 결정 단위로 가는지. README 3.3 보완이 필요하면 M10 이슈로.
3. **블록의 고위험 선언 위치.** `plumb.config.json` 의 `blocks.<name>.risk` 인지 `rules.yaml` 머리인지. 상단 바의 `⚠ n` 계산과 공유하므로 #5에서 정한다.
4. **결정 기록이 없는 규칙의 승인 허용 여부.** 첫 슬라이스는 허용(막으면 M3가 못 끝난다). M10 승인 모델에서 "결정 없는 완화·삭제는 승인 불가" 를 검토.
5. **목록의 기본 필터.** 전체인지 잠정만인지. §6.4 "매일 여는 화면이 아니라 쌓였을 때 비우는 화면" 을 따르면 잠정만이 맞지만, M3에서는 규칙이 몇 개 없으므로 전체로 시작한다.
6. **README 보완 후보.** 3.3 API 표에 `409` (제안이 바뀜) 와 기각 응답에 사유가 필수인지가 없다. #5 요청·응답 타입에서 정한다.
