# 운영 규칙

Plumb 개발에서 git과 서브 에이전트를 어떻게 쓰는지 정한다. Plumb 자체가 "역할 분리, 경계는 부탁이 아니라 설정으로"를 원칙으로 하므로, 개발 과정도 같은 규율을 따른다.

## 1. git 단위

### 1.1 대응

| git 단위 | 의미 | 규칙 |
|---|---|---|
| 마일스톤 | 작업 단계 하나 (M0~M10, `ROADMAP.md`) | 설명란에 **종료 증거**를 적는다. 종료 증거가 스크립트나 명령으로 확인될 때 닫는다 |
| 이슈 | 사람 하나 또는 서브 에이전트 하나가 **PR 하나로** 끝낼 수 있는 작업 | 반드시 템플릿(`.github/ISSUE_TEMPLATE/`)을 쓴다. **범위 밖**과 **완료 증거**가 비어 있으면 시작하지 않는다 |
| PR | 이슈 1개 해결. 예외적으로 밀접한 2~3개 | 템플릿의 "검증 증거"에 완료 증거 명령의 출력을 붙인다. squash merge |
| 라벨 | 영역 · 종류 · 병렬성 | 아래 1.3 |

### 1.2 이슈 템플릿 세 가지

- **작업(task)** — 목표 · 범위 · 범위 밖 · 완료 증거 · 의존 이슈 · 위임 가능 여부
- **설계 결정(decision)** — 결정 · 이유 · 기각한 대안 · 감수하는 것. 기획안 §6.2의 결정 기록과 같은 네 항목이다. 되돌리기 비싼 결정(프로세스 모델, 저장 형식, 공유 타입의 큰 변경)은 작업 이슈가 아니라 결정 이슈로 연다
- **버그(bug)** — 재현 절차 · 기대 · 실제 · 커밋

빈 이슈는 막혀 있다.

### 1.3 라벨

| 축 | 라벨 | 뜻 |
|---|---|---|
| 영역 | `area/core` `area/adapter` `area/ui` `area/testbed` `area/docs` `area/github` | 주로 바뀌는 패키지 |
| 종류 | `type/task` `type/decision` `type/bug` `type/spike` | spike는 검증 안 된 기술 가정을 확인하는 작업. 결과는 결정 이슈로 이어진다 |
| 병렬성 | `parallel/ok` | 2.1의 네 조건을 만족. 서브 에이전트에게 위임 가능 |
| | `parallel/blocked` | 선행 이슈가 머지되면 `parallel/ok`로 바뀐다 |
| | `env/local` | Claude 구독 로그인 · OS 샌드박스 · Docker가 필요해 사용자 머신에서만 가능 |

### 1.4 브랜치

- `main`은 보호한다. PR로만 머지한다. M1부터 CI(`pnpm check`)가 돈다
- 작업 브랜치 이름: `feat/<이슈번호>-<짧은이름>`, `fix/<이슈번호>-...`, `docs/<이슈번호>-...`
- 서브 에이전트는 자기 이슈의 브랜치에서만 작업한다. `main` 직접 커밋 금지

## 2. 서브 에이전트

### 2.1 위임 가능 조건 — 넷 다 만족해야 `parallel/ok`

1. **경계가 겹치지 않는다.** 이슈의 "범위"가 파일·디렉토리 단위로 적혀 있고, 같은 wave에서 동시에 도는 다른 이슈의 범위와 교집합이 없다
2. **공유 타입이 먼저 있다.** 이슈가 의존하는 타입·인터페이스(`packages/core/src/types/**`)가 이미 `main`에 머지되어 있다. 타입을 바꾸는 일은 그 자체로 별도 이슈이며, 순차로 한다
3. **완료가 명령 하나로 확인된다.** `pnpm test --filter ...`, 스크립트의 exit code 등. "동작하는 것 같다"는 완료 증거가 아니다
4. **로컬 전용이 아니다.** 에이전트 SDK 실행, 샌드박스, Docker가 필요한 이슈(`env/local`)는 사용자 머신에서 직접 한다

### 2.2 위임 프롬프트 — 고정 양식

기획안 §15.4의 네 항목(목표 / 출력 형식 / 읽어도 되는 것 / 건드리면 안 되는 것)에 완료 조건을 더한다. 항목을 빼거나 순서를 바꾸지 않는다.

```
목표:              이슈 #n 의 "목표" 한 줄 그대로
출력 형식:         브랜치 feat/n-<이름>, 커밋, PR 본문은 .github/PULL_REQUEST_TEMPLATE.md 대로.
                   마지막 응답은 세 줄만: 결과 / 변경 파일 / 실행한 명령과 결과
읽어도 되는 것:    <경로 목록>, docs/ROADMAP.md 의 해당 마일스톤 절, docs/CONTRIBUTING.md
건드리면 안 되는 것: <이슈의 "범위 밖" 그대로>, packages/core/src/types/**, 다른 이슈의 범위
완료 조건:         이슈의 "완료 증거" 명령이 통과한다.
                   통과 못 하면 PR을 draft로 올리고 실패 출력의 마지막 20줄을 PR 본문에 적는다
```

### 2.3 실행 방식

- 이슈당 서브 에이전트 하나. 작업 트리는 worktree로 분리한다
- 같은 wave의 이슈만 동시에 띄운다. wave가 끝나면(전부 머지) 다음 wave
- 서브 에이전트는 하위 에이전트를 띄우지 않는다. 깊이 1
- 서브 에이전트는 머지하지 않는다. PR은 오케스트레이터(세션 또는 사람)가 읽고 머지한다
- 범위 밖 파일을 건드린 PR은 머지하지 않고 이슈로 되돌린다. Plumb의 "범위 이탈 기록"과 같은 처리다
- 서브 에이전트의 보고는 입력으로 받지 않는다. 머지 판단은 PR의 "검증 증거"에 붙은 실행 출력으로만 한다
- 임시 파일(PR 본문 초안, 로그)은 **자기 worktree 안**에 둔다. 세션 scratchpad는 같은 wave의 에이전트끼리 공유되어 덮어써진다
- PR은 `gh api`(REST)로 연다. `gh pr create`와 GraphQL은 이 환경에서 쓸 수 없다

### 2.4 머지 절차 (오케스트레이터)

같은 wave의 PR 여러 개가 `pnpm-lock.yaml`과 `packages/core/src/index.ts`(re-export 줄)를 함께 바꾼다. 충돌은 서브 에이전트가 아니라 오케스트레이터가 푼다.

1. PR의 변경 파일이 이슈의 범위 안인지 확인한다 (`git diff --name-only origin/main...HEAD`)
2. 완료 증거를 직접 다시 돌린다. 에이전트가 붙인 출력은 참고일 뿐이다
3. 먼저 머지된 PR이 있으면 PR 브랜치에 `origin/main`을 머지한다. `pnpm-lock.yaml` 충돌은 main 쪽을 받은 뒤 `pnpm install`로 **재생성**한다(손으로 고치지 않는다). `src/index.ts` 충돌은 export 줄을 합치고 `biome check --write`로 정렬한다
4. 통합된 상태에서 `pnpm check`가 exit 0이면 PR 브랜치에 푸시하고 squash merge한다. 머지 커밋 제목은 `<type>(#이슈): 제목 (#PR)`
5. CI가 `pnpm check`를 `pnpm -r build`부터 돌리므로, 다른 패키지를 import하는 패키지는 빌드 순서(workspace 의존)에 기대면 된다
